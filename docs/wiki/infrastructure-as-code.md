# Infrastructure as Code (OpenTofu)

The infrastructure layer uses [OpenTofu](https://opentofu.org/) to reconcile the
Proxmox LXC and VM resources that Ansible then configures.

## Structure

Configuration is located in `infrastructure/`:

-   `main.tf`: Generic LXC/VM resources driven by the arbitrary `machines` map, plus checksum-verified image downloads.
-   `variables.tf`: Strict provider and machine contracts.
-   `provider.tf`: Proxmox provider configuration using `bpg/proxmox` `~> 0.111`; the lock file selects the exact signed artifact.
-   `outputs.tf`: Managed machine IDs, generated credentials, and the provider-managed template ID.
-   `generated.auto.tfvars`: Auto-generated by `homelab-toolkit generate` from `config.yaml` — do not edit manually.

## Getting Started

1.  **Install OpenTofu**: Follow instructions at [opentofu.org](https://opentofu.org/docs/intro/install/).
2.  **Generate tfvars**: Run `homelab-toolkit generate` to generate `infrastructure/generated.auto.tfvars` from `config.yaml`.
3.  **Define secrets**: Store `PROXMOX_API_TOKEN_ID` and `PROXMOX_API_TOKEN_SECRET` through the setup UI or secret CLI. Generation writes the combined provider token to gitignored `infrastructure/terraform.tfvars`.
4.  **Deploy**: run `homelab-toolkit deploy all`. The toolkit supplies the API
    token and CA bundle to OpenTofu; do not invoke a private-CA plan without
    that managed environment.

## Integration with Automation

The IaC layer provisions the exact enabled `machines` map from `config.yaml`.
Each machine declares its kind, address, prefix, gateway, public/private bridges,
resources, disks, and capabilities; `vmbr1` and `10.10.10.0/24` are only defaults.

`homelab-toolkit deploy all` performs generation, plan/apply, inventory
generation, host reconciliation, and the service rollout in order. Direct
`tofu` commands are useful for reviewing infrastructure changes, but the
toolkit remains the deployment entry point.

Normal deployment always reconciles the complete desired state. The only
targeted OpenTofu operation is the guarded retirement of one empty managed
machine. OpenTofu treats targeting as exceptional, so retirement additionally
requires an actor-bound plan, a recent restore checkpoint, an unchanged config
revision, and independent state plus Proxmox API verification. See
[ADR-009](../decisions/009-checkpoint-bound-machine-retirement.md).

Provider API TLS verification cannot be disabled. When `proxmox.tls_ca_file`
is empty, preflight retrieves the Proxmox cluster CA from
`/etc/pve/pve-root-ca.pem` over authenticated SSH, validates the PEM, and writes
a `0600` combined trust bundle under ignored `.homelab-state/trust/`.

## CI/CD with GitHub Actions

> **Status: Active.** `.github/workflows/ci.yml` is the single authoritative
> workflow for pushes to `main`, version tags, and pull requests. It performs:
> - locked Python 3.11–3.14 unit tests, coverage, Ruff, mypy, and dependency auditing
> - E2E ASGI smoke tests for every Web UI route
> - manifest generation, Ansible production-profile lint and syntax validation
> - installer BATS tests, clean-install smoke tests, and Docker Compose validation
> - OpenTofu validation and a clean-root CLI lifecycle test
> - full-history secret scanning
> - manifest-discovered custom image build, smoke, dependency audit, publication,
>   and provenance attestation

GitHub Actions handles linting, testing, validation, and trusted image publication.
Local development uses the same locked tools through `make ci` or
`scripts/local-ci.sh`.

### How It Works
- GitHub Actions workflows trigger on push to main and pull requests
- The CI workflow validates all scripts, playbooks, Compose files, and infrastructure
- Trusted pushes build manifest-declared images and publish them to `ghcr.io`
- Workflow files go in `.github/workflows/` (standard GitHub Actions YAML)

### Security Note
The runner has Docker socket access on the host. Only grant repository write access to trusted users — workflow code runs with host-level Docker privileges.

### Handling VM Reboots

When a workflow updates Docker Compose configurations and runs `docker compose up -d`, only containers are restarted — **the VM does not reboot**. Docker Compose performs rolling updates by default:

1. Pulls new images (if changed)
2. Stops and removes only the changed containers
3. Creates and starts new containers
4. Other containers continue running

For changes that require a VM-level reboot (kernel updates, host networking changes), use the toolkit instead:

```bash
homelab-toolkit deploy all
```

The Gitea runner itself survives `docker compose up -d` because it is part of the same compose project — Docker detects it hasn't changed and leaves it running.
